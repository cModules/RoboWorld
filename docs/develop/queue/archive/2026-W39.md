- [x] **顺带挖出一个本地构建陷阱（已记进 `docs/manual/打包说明.md` 常见问题）**：
  `python -m build` 会**复用 `build/lib/`**，删掉/搬走的模块其旧副本仍在，
  被增量复制进 wheel。实测：wheel 里的 `core/cli.py` 与 `build/lib/core/cli.py`
  **md5 一致**，导致"本地 wheel 校验"一度不可信（前几轮报的包内容同样被污染）；
  清掉 `build/ dist/ *.egg-info/` 重建后，`core/` 只剩 7 个内核文件、陈旧模块归零。
  CI 从干净 checkout 构建 ✅ 不受影响。

- [x] **更正 + 修复：C++ 侧从未真正改名，`PYBIND11_MODULE` 与产物名不一致（2026-09-26）**。
  核查"编译集成"链路时发现 `core/src/binding.cpp` 里仍是
  `PYBIND11_MODULE(orolp_core, m)`，而 CMake 是
  `set_target_properties(_core_native PROPERTIES OUTPUT_NAME "core_native")`
  ——**pybind11 要求两者一致**（模块名决定 `PyInit_<name>`），不一致则编出来的 `.so`
  名字对不上、`core/__init__.py` 的 `from . import core_native` 永远失败，
  而这个失败被 `try/except` 静默降级成"加速层不可用"，所以一直没人发现。
  **根因：最早那轮 `orolp→core` 全量改名的文件类型白名单里没有 `.cpp/.h`**，
  而事后"残留清零"的 grep 也用了同一套白名单——**验证手段与执行手段共用了同一个盲区**，
  于是两处都看不见它。  同一盲区还漏掉 `docs/DOMAIN_ARCHITECTURE.svg`（`.svg` 也不在名单里，
  里面写着 `orolp/app/` 与 `_orolp_core`）。
  已全量修正：C++ 源码 14 处（`namespace orolp`→`namespace core`、`PYBIND11_MODULE(orolp_core)`→
  `core_native`、`using namespace orolp`）；SVG 3 处（旧产品名、加速层名、GUI 债务数量由 4 改 2）。
  **教训：改名后的核查不能用"只查我改过的文件类型"——必须不限类型全仓扫（本轮已用
  `grep -rniI orolp .` 不限后缀复核，仅剩 `BUILD_QUEUE`/`ROADMAP` 里描述改名本身的历史记录）。**
